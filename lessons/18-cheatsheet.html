❤️ When you STILL need JavaScript

💾
Saving and remembering

Remembering a choice (like dark mode) for next time, saving a form draft.

🌐
Talking to servers

Loading data, live search, sending forms without reloading, chat.

🧮
Real logic and maths

Prices, baskets, filters, anything where the number is used and not just shown.

⏱️
Timers

Auto-play carousels, countdowns, "session expires in 5 minutes".

📊
Tracking and analytics

Measuring what people click (with consent!).

🎮
Truly interactive apps

Editors, games, drag-and-drop builders, maps.

🧭 The golden rules

Before you write JS or npm install a UI library, ask: "can HTML or CSS already do this?"
If JS is only moving stickers (classes) around for CSS, there's probably a CSS feature for it.
Use new features as a staircase 🪜: everyone gets a working page, modern browsers get the extras.
Check support on web.dev/baseline and caniuse.com.
JavaScript isn't the enemy. Use the brain for brain jobs, and let the paint do the painting.

⚠️ When NOT to delete it

🌐It isn't widely supported yet

Check the lesson's badge.

→ Keep a fallback, or keep the JS for now
🧩The built-in version can't do the job

A type-to-search dropdown, a carousel that plays by itself.

→ Keep the JavaScript
🦯A CSS trick breaks keyboards or screen readers

Hacks that only look right.

→ Use real HTML elements
🐘The real problem is somewhere else

A 2 MB picture, a slow server.

→ Measure first
🏗️A big rewrite for a tiny gain

Touching a stable page just for this.

→ Change it when you're already working on it

🪜 The order: always the least powerful tool first

1🧱 HTMLthe content, plus built-in behaviour
2🎨 CSSlooks, states and animation
3🧠 JavaScriptonly the brain jobs

↗ Each step up is more powerful, but also more to download, run and break. One component saves a little; a whole site of them adds up.

🔬 Don't take my word for it. Measure your Web Vitals before and after you delete some JavaScript.
