Why we're deleting JavaScript

We're not anti-JavaScript. We're anti-using-JavaScript-for-things-the-browser-already-does. Here's why it matters, and why now.

Jump to:1🎯 The thesis2🏠 What each layer does3📊 The numbers4📈 What CSS improves5🧊 Frozen brain6🧪 Playground7✅ Browser support

1 · The thesis 🎯

❌ Not this

"Never use JavaScript."

✅ This

Let HTML & CSS do every job they already can.
Keep JavaScript for the jobs only it can do.

Why? Because every line of JavaScript costs your visitors something. Hand the job to HTML & CSS and they win it back:

📦

JavaScript costs download time✅ Less to download

👷

It keeps the one worker busy✅ Taps answered sooner

⭐

It can drag down Google's scores✅ Better Web Vitals

🧯

If it fails, the feature fails✅ Still works without it

😓 A JavaScript feature: 5 steps before your first tap works

  1. 📦Download the JS file
    over the network
  2. 🔍Parse and compile it
    into instructions the chip can run
  3. ⚙️Execute it
    the main thread is blocked
  4. 👂Register event listeners
    "when clicked, do this"
  5. 🙂Now it works
    unless the file never arrived, or one line threw 💥

😎 A built-in HTML feature, styled by your existing CSS

  1. 🧠Behaviour is built into the browser
    opening, closing, Escape, focus: nothing to download
  2. 📄Works as soon as the HTML arrives
    your CSS in the <head> makes it look right from first paint
  3. ♿Keyboard and screen-reader support
    come with it, for free
✅

Less code = less to write, test, review and fix. Faster pages = less to download. Accessibility for free = the browser handles keyboards and screen readers. More robust = still works if a script fails to load.

❤️

JavaScript is not bad. We still need it for real "brain" jobs: saving data, talking to servers, complex logic. The rule is simple: don't use a brain to do a paintbrush's job.

2 · What each layer does 🏠

🧱

HTML

= structure and content

Says what is on the page: a heading, a button, a menu. Also carries semantic meaning: this is a dialog, this is a nav.

"There is a button here that says Buy."
🎨

CSS

= appearance and state

Says how things look and which state they're in: colours, sizes, animations, open/closed, hovered, checked.

"Make the button green. Show the menu when it's open."
🧠

JavaScript

= behaviour and data

Says what happens: server calls, complex logic, timers, anything that needs real computation.

"When someone clicks Buy, POST to the cart API."

🤝 Objections, answered

"But the browser waits for CSS too!"

Yes. One wait. It already happened.

Every page loads a stylesheet. That one CSS wait is unavoidable. The features in this talk are a few extra lines added to that same file. No extra wait.

With a JS solution you pay twice, in order:

  1. CSS loads and blocks first paint. (Same as always.)
  2. JS file downloads. (Extra network wait.)
  3. JS executes on the main thread. (Extra CPU wait.)
  4. Feature becomes usable. (After all three.)

With CSS alone you stop at step 1. The feature is ready at first paint.

Using CSS-in-JS or CSS modules in React? Same story. The extracted CSS ends up in a stylesheet the browser loads once and caches. The extra rules for these features add a few bytes. Still one wait, still no JavaScript to execute for the feature itself.

"Just add defer or async to the script."

They change when the JavaScript runs, not whether it runs. The same code is still downloaded and executed on the same main thread. Until then the feature doesn't work, and things can jump when the script mutates the DOM.

"Won't all this CSS bloat my bundle?"

CSS is parsed once and cached. It is never executed. No long tasks, no main-thread cost.

Your CSS grows a little. Your JavaScript shrinks a lot. We measured every "after" example in this talk:

Before: JS2.8 KB
Before: CSS0.7 KB
After: CSS1.8 KB

All 15 lessons with live code, gzip compressed. After: 0 KB of JavaScript.

  • Each feature's CSS ships only on pages that use it, same as its JavaScript would have.
  • Real projects use libraries. Removing the library removes its CSS file too.

And unlike defer or async:

🧠 defer (JavaScript)
  1. Page appears.
  2. JS file downloads (~700 ms).
  3. JS parses and executes on main thread.
  4. Feature works.
🎨 CSS version
  1. Page appears.
  2. Feature works. Already done.

0 ms download. 0 ms main-thread cost.

"My machine is fast. Who cares?"

Your visitors aren't on your machine. An ordinary phone runs the same JavaScript 3–6× slower, and the typical phone page is blocked for 1.9 seconds while it loads. Try the "Google's phone test" in the playground.

"So JavaScript is bad?"

No. JavaScript is the right tool for server calls, real logic, timers, and anything stateful. The question is just: can HTML or CSS already do this? If yes, use them.

4 · What CSS actually improves 📈

This is not about when JavaScript loads. It is about removing the cost entirely. CSS has no download phase, no parse phase, no execution phase on the main thread. The browser already handles it as part of normal rendering.

LCP
Largest Contentful Paint

Good: under 2.5 s. JS delays it by blocking the parser and holding up first paint. CSS features are already part of the paint.

INP
Interaction to Next Paint

Good: under 200 ms. JS running on the main thread blocks tap responses. CSS animations run on the compositor thread and never block.

CLS
Cumulative Layout Shift

Good: under 0.1. JS mutates the DOM after content is visible, causing things to jump. CSS state is resolved at first paint: no jump.

⚖️

defer and async do not fix these. They reschedule when JavaScript runs, but the download still happens, the execution still happens on the main thread, and the feature is still dead until then. The Core Web Vitals row for INP, CLS and main-thread blocking stays red regardless of how you load the script.

The browser already knows how to open a menu, show a tooltip, animate a transition. CSS just tells it to. JavaScript re-teaches it every page load. That re-teaching is what costs LCP, INP and CLS.

Both balls slide back and forth. JavaScript moves the top one, CSS moves the bottom one. Press the blue button to block the main thread for 3 seconds, as a heavy script does on a slow phone.

Press the blue button, then quickly click "Click me" a few times.
🔍

Why? The JS ball calls requestAnimationFrame, which needs the main thread every frame. The CSS animation runs on the compositor thread, which is independent. That's why transform and opacity animations stay smooth even when the main thread is saturated.

📏 What each metric means

TTFB

Time To First Byte

First byte of the page from the server. Depends on the server, not JS or CSS. Same for all four shops.

FCP

First Contentful Paint

First text or image on screen. Shop 2 is late here. It waits for its script. Good: < 1.8 s.

LCP ⭐

Largest Contentful Paint

When the main content appears. Good: < 2.5 s. Core Web Vital, used in search ranking.

Ready

Visible and interactive

When you can see it and buttons work. Shops 3 and 4 look ready before they are.

CLS ⭐

Cumulative Layout Shift

How much things jump while loading. 0 = nothing moved. JS shops hide answers after you've seen them. Things jump. Good: < 0.1.

TBT

Total Blocking Time

Time the main thread was blocked by long tasks (> 50 ms). Good: < 200 ms.

INP ⭐

Interaction to Next Paint

Tap → screen update. Fills in after you interact with a shop. Good: < 200 ms. Core Web Vital.

⭐ = Core Web Vital, one of three scores Google uses in search ranking. Green = good, yellow = needs work, red = poor.
